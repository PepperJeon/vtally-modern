# Decisions

Conclusions only. For the reasoning, follow the pointer. Where two sources genuinely disagreed, it's flagged, not resolved.

## Architecture

- **`src/{server,client,shared}` split**, enforced two independent ways: `.eslintrc.js` `no-restricted-imports` bans `**/server/**` (and bare `events`/`fs`/`net`/`dgram`/`http`/`child_process`) from `src/client/**` and `src/shared/**`; `vite.config.ts`'s `resolve.alias` maps those Node builtins to a throwing stub (`src/client/lib/noNodeBuiltins.ts`) so a leak fails the *build*, not just lint. Neither mechanism alone was sufficient — eslint doesn't catch a bundler quietly polyfilling `events`, and the alias doesn't catch a path-based `server/` import. Why the eslint rule uses string patterns, not `{group, message}`: that form needs ESLint 8, and `react-scripts` (still a devDependency, still the source of the `react-app` eslint preset) pins ESLint 7. *(`docs/design/module-split.md` §2–3, `.eslintrc.js`, commit `adaf82d`)*
- **`shared/mixer/ids.ts`** is a new leaf module (`ATEM_ID`, `OBS_ID`, `VMIX_ID`, etc. + `MixerId` union) so 8 client Settings components stop importing a server Connector class just to read `.ID`. Server connectors now re-export from it instead of redeclaring the literal — one source of truth. *(module-split.md §1)*
- **Dev-proxy direction inverted.** Was: express:3000 serves the CRA dev build, proxying nothing. Now: Vite:3001 is the dev entry point and proxies `/socket.io` (`ws: true`) to express:3000; production build output is `dist/client`, served by express. *(module-split.md, `vite.config.ts`)*
- **Backend runs standalone under `ts-node` today** (`npm run start:backend` → `ts-node --project tsconfig.server.json src/server/server.ts`). Electron scaffolding landed in Phase 4 — see the Electron section below. *(native-deps.md §4)*
- **socket.io 2 → 4 (unit 2b), server and client together.** The 44 domain events crossed untouched: `ServerSideSocket`/`ClientSideSocket` in `hub/src/shared/lib/SocketEvents.ts` are hand-rolled *structural* types, not socket.io's own `Server<…>`/`Socket<…>` generics, so the wire contract is invisible to the version bump (verified, not assumed). Only the three `socketIo.Socket` casts needed porting — `server.ts` (`setMaxListeners`) and `WebTallyDriver.ts` (`.connected`, `.handshake.address`).
- **The six `events.*.unsubscribe` events are GONE, not just flagged.** `coverage-gaps.md` lists `events.{mixer,program,config,tally,channel,tallyLog}.unsubscribe` under "likely dead code, worth a one-line confirmation" — that confirmation happened in 2b and they were removed, from both `ClientSentEvents` and their `server.ts` handlers. No client emitted any of them anywhere in `src/client/**` or `cypress/**`; the only live unsubscribe is `events.webTally.unsubscribe` (`WebTallyPage.tsx`), which stays. **Why removing them was safe rather than merely tidy:** `SocketAwareEvent.register()` attaches its own `"disconnect"` listener, so every pipe tears itself down when the socket goes away — the explicit unsubscribe was never the mechanism keeping listeners from dangling. This also retired both known wiring bugs in that block for free (the duplicate `events.program.unsubscribe` handler, and `configEvents` being attached to it instead of `events.config.unsubscribe`) — fixing the second would have meant renaming a handler nobody calls.
- **socket.io's heartbeat is pinned to `pingInterval: 1000, pingTimeout: 2000` as a safety requirement, not a preference.** v4 relaxed engine.io's defaults for flaky mobile networks (25s/20s), which lets a web tally — a phone taped to a camera — keep showing its last state for up to 45s after the hub dies. The dangerous case is a stale *idle* while the camera is actually live: the operator believes they are safe while broadcasting. v2 noticed in about a second; this restores that. The cost objection (phones on battery) is real in principle but not here — `WebTallyPage` already holds a wake lock and runs a full-screen bright fill, so the radio is awake and the screen dominates the power budget. **Do not relax these toward the defaults to save traffic without replacing the guarantee.** This regression was caught by `hub-disconnected-banner.spec.ts` and by nothing else.
- **Eight of `useSocket.ts`'s client lifecycle listeners were inert, and had been for years.** Found while porting: `"disconnected"` was a typo for `"disconnect"` and never existed as a socket.io event at all; `connect_timeout`/`reconnecting`/`reconnect_failed` are v2-only; `reconnect`/`reconnect_error` are Manager events in v4, not Socket events. `connect` / `disconnect` / `connect_error` is the complete v4 client lifecycle and is now what's registered. The dead names were also declared on `ClientSideSocket`, so the type actively advertised listeners that could never fire — that's how the outage signal stayed lost. `connect` is untouched, so the four trackers' re-subscribe path is unchanged, and `ConfigTracker`/`MixerTracker` still deliberately don't re-subscribe (that's unit 2d).
- **`EventEmitter`/`events` removed from the client bundle.** Vite doesn't polyfill it (webpack silently did). Replaced with `hub/src/client/lib/Emitter.ts`, 43 lines of `on`/`off`/`emit`/`listenerCount`/`removeAllListeners`. **Correction, made when the React 19 upgrade tried to cash this in:** this entry used to claim the replacement was a `Tracker<TSnapshot>` base class with `subscribe`/`getSnapshot`, "shaped to make the 1a conversion a drop-in swap". No such class exists and none ever did — the six trackers each `extend Emitter` and expose an ordinary public field. See the 1a entry under Deferred work for what that actually costs. *(module-split.md §6)*

## Build

- **Vite 5, not Vite 8.** Not a preference — Vite 8's rolldown-based dep optimizer miscompiles `@material-ui/styles`' CJS (emits an unassigned `var import_react$1`), which throws inside `ThemeProvider` and fails every Cypress spec in `before-each`. React 17 + MUI 4 is a 2021 stack; Vite 5's esbuild-based line is what it's actually tested against. Revisit when MUI is gone (Phase 3). *(commit `adaf82d`)*
- **TypeScript 4.5 → 5.9** was required twice over, not a nice-to-have: Cypress 15's bundled lodash typings don't parse under 4.5 (TS1005), and 5.9 was needed regardless for the Vite/Vitest 2 line. *(commit `fb96fb6`)*
- **Cypress 6 → 15**, with the Cypress 10+ layout (`cypress/e2e/`, `cypress.config.ts`, `specPattern` pinned to `**/*.spec.ts`). The specs keep the `.spec.ts` suffix deliberately — Cypress 15's default `**/*.cy.*` pattern would match zero files and exit 0, i.e. fail upward silently. `baseUrl` moved 3000→3001 (Vite is now the dev entry point). *(commit `fb96fb6`)*
- **No `NODE_OPTIONS=--openssl-legacy-provider` anywhere.** That was a workaround for old webpack + new OpenSSL; gone with CRA. Confirmed absent from every script in `hub/package.json`.
- **Vitest 2, not 3** — pinned alongside the Vite 5 decision above, same rolldown-adjacent reasoning; not separately re-litigated.
- `react-scripts` and MUI 4 are **still real devDependencies**, not cruft: `react-scripts` supplies the `react-app` ESLint preset (and pins ESLint 7, see Architecture); MUI 4 is still the live UI library until Phase 3.

## Gates (`scripts/verify.sh`)

Order: `tsc` (app + server) → unit tests vs baseline → production build → bundle-leak check → Cypress vs baseline. Baseline numbers live in exactly one place, `scripts/baseline.json` — never edit a number inline elsewhere. **The implementer does not sign off on its own work**: a phase is verified by someone other than whoever wrote it, running this script; a phase passes when it exits 0. *(scripts/README.md)*

- **The bundle-leak probe checks five packages by name, not one bare string.** It originally grepped for bare `"obs-websocket"`, which also matches operator-facing copy in `ObsSettings.tsx` ("install the obs-websocket plugin") — Phase 1 correctly refused to edit visible product text just to make a grep pass, and reported the gate as *failing*. The gate was wrong, not the code. Fixed to probe `obs-websocket-js`, `nodemcu`, `atem-connection`, `@julusian`, `child_process` independently — five greps returning zero says more than one alternation returning zero. *(commit `c07bdef`)*
- **`got < want` fails; `got == want` passes; `got > want` passes with a note to consider raising baseline.** Nothing raises the baseline automatically — it's a deliberate, reviewed diff to `baseline.json` (as happened once already, see Testing below).
- Latest `verify.sh` run: **all gates PASS, zero Cypress failures.** Deliberately not restating the counts here — `scripts/baseline.json` is the single source of truth and this line has already gone stale twice by repeating numbers next to it. Run the script for current figures. (Historical note, for anyone diffing: this bullet previously claimed "unit 324/324, Cypress 53/53"; both were prose lag behind `baseline.json`, not a second opinion.) `tally-settings.spec.ts` remains the known flake — it has been measured at 10, 12 and 13 passing across consecutive runs of the same tree (racy `cy.task('tallyLastCommand', ...)`), so treat a number in that band as noise, not signal.

## Testing — what the numbers mean, and what has no net

- **Two different baselines exist and are not in conflict** — they describe different phases. `BASELINE.md`'s headline numbers (25/26 unit suites, 238/244 unit tests, 53/73 Cypress) are Phase 0's raw as-measured figures on the pre-restructure tree. The live gate in `scripts/baseline.json`, and the number the Phase 1 merge commit (`80bf064`) reports, is the **Phase 1** baseline: 32 unit suites / 324 unit tests / 53 Cypress — raised deliberately after Phase 1 landed more passing suites. Today's tree has 32/33 suites and 324/330 tests passing (against that 32/324 baseline) — the 1 remaining red suite is the known `VmixConnector.spec.js` defect below. If you see "25/238" and "32/324" in different documents, that's Phase 0 vs. Phase 1, not disagreement.
- **A passing gate is not the same as a trustworthy one.** `docs/design/test-audit.md` grades every unit spec's assertion quality, not just pass/fail: 12 suites solid (real regression gates), 7 partial (catch structural breakage, miss value regressions), 1 (`NullConfiguration.spec.ts`) worth zero — both its tests assert nothing. Specific blind spots: `ObsConnector.spec.ts`'s 19 `waitUntil` polls compare a live value against a freshly-allocated array literal, so they resolve on the first tick regardless — real assertions still run after, but the wait itself is a fixed sleep, not synchronization. Five mixer-config "has a default" tests use `toBeTruthy()` on a getter — blind to *which* default; nothing would catch `ObsConfiguration.defaultPort` silently changing from 4444 to 4455.
- **Three units had zero regression net when that audit was written** — two of the three claims have since expired, and the wording is kept only so a doc still repeating them reads correctly against history. **1a** (`useSyncExternalStore`) — *expired*: seven tracker specs now exist (`src/client/hooks/tracker/*.spec.ts` + `useTallies.spec.tsx`), added by the Phase 1 restructure. **2a** (`channelsByMixer`) — its three gating suites were `midi`-blocked at audit time; the `midi`→`@julusian/midi` swap unblocked them, which means they can run, not that they cover the right things. **2b** (socket.io v2→v4) — *expired*: the Cypress gate is measured and green, and it did its job, catching 2b's one real regression (see the socket.io entry under Architecture). Live numbers: `scripts/baseline.json`, not this list. *(BASELINE.md, verbatim as of the audit: "there is currently no regression net at all for module 1a..., 2a..., and 2b...")*
- **`VmixConnector.spec.js`'s failure is a one-line spec defect, not environment coupling** — it binds its mock server to `'localhost'` while the sibling `RolandV60HDConnector.spec.js` binds to `'127.0.0.1'`; on a machine where `localhost` resolves to `::1` first, the IPv4-only IP validator rejects only the Vmix spec. Left failing in the baseline deliberately (correct call — it's real red, not noise), fix is a deferred one-liner. *(commit `490d804`)*
- Recommended-but-not-yet-applied ordering (test-audit.md, advisory): write tracker specs before the 1a refactor starts, not after.

## The Cypress boundary

Two categories of allowed spec edits — do not conflate them.

1. **Already done, mechanical, path-only.** Migrating to `src/{server,client,shared}` broke 10 import lines across 5 spec files. `git diff -U0 cypress/e2e/` for that change was 10 lines, all `import`, zero assertions/selectors/testids touched. *(commit `fb96fb6`)*
2. **Pre-authorised for the Phase 3 MUI→Tailwind/shadcn rewrite, not yet exercised.** Exactly two edits, and nothing else, ever:
   - `configVmix.spec.ts:45,50` — the one real MUI-internal-class dependency (`.MuiFormHelperText-root`, no Tailwind equivalent). Fix requires adding `data-testid="vmix-port-warning"` to the redesigned component and asserting on that instead.
   - `smoke.spec.ts:14,17,20` — nav-copy `cy.contains("Configuration")` etc. Update once redesign nav copy is finalised, using new `nav-configuration`/`nav-flash`/`nav-tallies` testids.
   
   Everything else is off-limits — weakening an assertion, `.skip()`, changing a testid string, anything. **If a spec goes red and the fix isn't one of these two, the fix belongs in the component. A red test you can't fix by fixing the component is a signal to escalate, not to route around.** *(spec-changes.md §1–3)*
- (Correction embedded at source: `ui-contract.md`'s Hazard H6, "duplicate testid per field," was traced and retracted — the string appears twice in source as a prop but renders as `data-testid` on exactly one DOM node. No spec or component change needed for it.)
- **A green Cypress run proves DOM/testid/state-attribute parity and protocol-output parity. It does not prove the two-edit rule was followed** — only a human (or a separate, non-implementing agent) reviewing `git diff` against `cypress/` line-by-line proves that, every time. *(spec-changes.md §3, §5)*
- **What Cypress doesn't cover at all**, ranked by (likelihood Phase 3 breaks it) × (cost if broken live): (1) `WebTallyPage` brightness/highlight are asserted by attribute (`data-brightness`), not visible effect — the attribute can be right while the screen is wrong, on the one screen a studio actually watches; (2) the hub-disconnected banner has zero coverage; (3) reconnect/crash-restart is known-missing (two named `it.skip` stubs); (4) every dialog's Cancel path is untested, Save is tested everywhere; (5) `tally.remove` has an unfinished `it.skip`. *(commit `e805e10`)*

## Electron (Phase 4)

- **No IPC layer, no preload API.** The app already has a client/server seam — socket.io — and `electron/main.ts` starts the existing server in-process and points a `BrowserWindow` at it, so the renderer's `io()` (no URL) works unchanged in all four run modes. `electron/preload.ts` exists and is deliberately empty; `contextIsolation: true`, `nodeIntegration: false`, `webSecurity: true`.
- **`server.ts` is now `export async function startServer(opts): Promise<ServerHandle>`** plus a `require.main === module` CLI shim. `bin/vtally` → `forever-monitor` → `src/server/server.js` is unchanged. The handle carries the *bound* port (Electron asks for `port: 0`) and a `close()` that persists config **before** closing socket.io and the UDP socket — `AppConfigurationPersistence` debounces by 500 ms, so quitting inside that window used to drop the last change. `before-quit` calls it.
- **`app.requestSingleInstanceLock()`**, because two hubs fighting over UDP 7411 is a support ticket nobody diagnoses. `UdpTallyDriver.close()` (new) clears its two intervals and releases the socket.
- **Config writes are atomic** — temp file then `rename`, so a hub that loses power mid-write keeps the previous `~/.wifi-tally.json` instead of a truncated one. Two lines; a real field failure mode for gear that gets unplugged rather than shut down.
- **`"npmRebuild": false`, prebuilds-first.** `@julusian/midi` and `@serialport/bindings-cpp` are N-API and their prebuilds load inside Electron unmodified — **verified in a packaged build, not `electron .`**: both `require()` fine from inside the app and `SerialPort.list()` enumerated 3 real devices. Leaving electron-builder's automatic `@electron/rebuild` on *breaks packaging outright* on an unrelated module — `forever-monitor` (npm/Pi supervisor, never loaded by Electron) pulls a NAN-era `fsevents` that cannot compile against Electron 43's V8. `@electron/rebuild` remains the fallback, run by hand.
- **`"extends": null` is load-bearing.** electron-builder auto-applies its `react-cra` preset whenever `react-scripts` is a dependency — which it still is, for the ESLint preset — silently rewriting `main` to `build/electron.js` and `files` to `build/**`. Packaging fails with "entry file is corrupted" until the preset is turned off. Remove this only after `react-scripts` is gone.
- **Output dirs are separate on purpose.** electron-builder excludes its own output directory from `files`, so `directories.output` is `release/` and the app tree is `dist/app/` (`tsconfig.electron.json`, rootDir `.`, a self-contained copy of `electron/ + src/server/ + src/shared/`). It is *not* added to `tsconfig.server.json`, whose inferred rootDir is `src/` — adding it would push every server output one level deeper and break `bin/vtally`'s hardcoded `../src/server/server.js`.
- **Firmware path**: `NodeMcuConnector.getLocalFiles()` now tries `process.resourcesPath + "/esp8266"` first (Electron `extraResources`, unpacked, outside asar) and keeps *both* existing fallbacks unchanged. Verified in the packaged app: files resolved from `…/Contents/Resources/esp8266`. `extraResources` pointing at a missing `../tally/out` is a warning, not a build failure.
- **Electron's gate is `hub/e2e/electron-smoke.spec.ts`** (Playwright-Electron, one test): launch the *packaged* app, assert `[data-testid=page-config]` renders and both native modules load. Cypress cannot cover Electron and this is not trying to be a suite.

## Known bugs — recently closed

Both entries below were fixed in Phase 2d (`768416c`, `7759e4b`) and are kept, not deleted, so a design doc still describing them as open reads correctly against history.

- **RESOLVED — `/flasher` no longer crashes the backend.** `hub/src/server/flasher/NodeMcuConnector.ts`'s `listFiles()` (the renamed/relocated `getLocalFiles()`) now wraps its `readdir` calls in a try/catch (~lines 87–91) and returns `[]` on total failure instead of letting the rejection escape unhandled. That lets the "firmware not available" state the code already implemented get reached, instead of killing the ts-node process. *(commit `7759e4b`)* — original bug, for history: `getDevice()` called `getLocalFiles()` outside its own `try` block; both firmware dirs (`esp8266/`, `../../../tally/out`) are missing in a hub-only checkout, so the rejection was unhandled. *(BASELINE.md, commit `848bd24`)*
- **RESOLVED — `finally`-block disconnects no longer clobber real errors.** A new `safeDisconnect()` helper (line 154) now guards all three call sites — `getDevice()`, `program()`, `writeTallySettingsIni()` (lines 236, 286, 346) — fixed on our side rather than waiting on the fork: the root cause was nodemcu-tool's `isConnected()` reporting `true` after a failed `connect()`, so `disconnect()` rejected with "Port is not open" and overwrote the clean error the `catch` block was returning. *(commit `7759e4b`)* — original bug, for history: same three `finally` blocks called `disconnect()` unconditionally. *(native-deps.md §3, §6)*
- Same commit (`768416c`) also re-pinned `nodemcu-tool` to a commit SHA, closing `BASELINE.md` Deviation #2 — `npm ci` installs cleanly again (verified: 137 packages, only pre-existing deprecation warnings, zero nodemcu-tool errors).

## Deferred work, and its trigger

- **`useSyncExternalStore` (unit 1a)** — trigger fired (React 19 landed), work **deliberately not done**, and the estimate that deferred it was wrong. It is not a drop-in swap: there is no `Tracker` base class to swap (see the correction under Architecture), so the subscribe/getSnapshot surface has to be invented, and it has to be invented *per snapshot*, not per tracker — `ConfigTracker` alone publishes ten independent values, `ProgramTracker` publishes a correlated pair that `useProgramPreview` returns as a tuple (one hook, two snapshots), and `TallyLogTracker` is keyed by tallyId so it needs a cached snapshot *per key*. Thirteen hooks across `useConfiguration.ts`, `useChannels`, `useMixerInfo`, `useProgramPreview`, `useTallies`, `useTallyLog` are rewritten, plus the six trackers. That is the whole client data layer, and putting it in the same commit as a React major and the removal of the UI library would mean that if the Cypress suite went red, nothing would say which of the three did it. Still worth doing; wants its own change.
  - **The one landmine, so it isn't rediscovered:** `tallylog.ts` re-emits the *same array instance* (`entry.push(theLog)`), and `useTallyLog` currently copies it in the listener (`Array.from(logs)`) to force the re-render. A `getSnapshot` that copies is an infinite loop — React throws "The result of getSnapshot should be cached". The copy has to move into the *update* path (`this.logs.set(tallyId, [...entry, theLog])`). `TallyTracker` and `ChannelTracker` already `map()` a fresh array per event and are safe as-is.
- ~~**`MixerSelection` registry + 8 components' `defaultProps`**~~ — done before Phase 3, as required. React 19 landed on top of them.
- **`<React.StrictMode>` is gone from `main.tsx`, and cannot come back while react-router is on v5.** StrictMode remounts every component once (mount → unmount → mount) on the *same* instance. react-router v5's `<Router>` subscribes to history in its **constructor** and unsubscribes in `componentWillUnmount`, so the simulated unmount drops the subscription and the second mount — no constructor — never restores it. The router then renders the initial URL and ignores every `history.push`: deep links work, every in-app `<Link>` click silently does nothing. React 17 never double-invoked lifecycles, which is why this stayed invisible until the React 19 upgrade turned it into three red Cypress tests (`smoke` "Navigation is working", `tally-logs` "should be linked from the tally list", `webtally` "Web Tallies are linked" — all failing on click-to-navigate while the deep-link tests beside them passed). **This is the concrete cost of staying on react-router v5, and it is the strongest argument yet for the v6+ migration**; putting StrictMode back is a v6 follow-up, not an independent change.
- ~~**React 19 + delete Material-UI**~~ — **landed.** MUI's `<CssBaseline />` was replaced by an explicit `@layer base` block in `index.css` rather than by Tailwind's preflight; the reasoning, and why preflight stays out even though the thing blocking it is gone, is in the comment at the top of that file. `react-full-screen` was replaced by the native Fullscreen API (it peered on react ^16.8), and `react-scripts` — dead since Phase 1 — was removed with it.
- **`--legacy-peer-deps` is still required, for a new reason.** `react-full-screen`, the documented cause, is gone; a plain `npm install` now fails on `@types/node@12` against vite's `peerOptional @types/node ^18 || >=20`. Bumping `@types/node` is a one-line change with an unknown blast radius across `src/server`, so it was not ridden along on the React upgrade.
- ~~**Electron scaffolding**~~ — **landed in Phase 4**, see the Electron section under Architecture.
- **Loud UI failure for the flasher lazy-load stub** — the existing Proxy-stub fallback for missing native `nodemcu-tool` bindings only `console.error`s today. Plan (not yet implemented): extend the `flasher.device` socket event to carry the real caught-error string instead of a fixed `FLASHER_UNAVAILABLE` message, with a distinct frontend state. *(native-deps.md §6)*
- **`tally-settings.spec.ts`'s 2 failing tests** ("operator brightness", "stage color scheme") — known flake (racy `cy.task`), not triaged as part of any phase yet.
- **`VmixConnector.spec.js`'s `::1`/`127.0.0.1` bind mismatch** — one-line fix, deferred, not yet scheduled.
- **`npm audit`: 5 high-severity vulnerabilities** flagged on the `nodemcu-tool` git dependency's transitive tree at last `npm ci`. Not yet actioned or triaged anywhere.
- **WebTallyPage: disconnected-vs-loading is design-addressed but attribute-incomplete.** `design-screens.md` §4.7 does close the ambiguity — hub-socket-lost still falls back to `data-color="loading"`, but the design adds a conditional `⚠ Disconnected — reconnecting` text line once a real disconnect is observed. That's the fix for `coverage-gaps.md`'s `it.skip("indicates when connection to server is broken")`, but it's text-only: unlike the redesigned tally card (new `data-health` attribute, `design-components.md` §1.1/§1.3) and the IndexPage status pills (`data-connected`, `design-screens.md` §1.4), WebTallyPage gets no equivalent attribute. The disconnect condition is only assertable via text content, not a stable selector — the gap spec will need a `data-connection`/`data-health`-style attribute on `page-tally-web` to match the pattern used everywhere else transport health is shown.
